# Platform findings

Checked 2026-09-09, product scope updated 2026-09-11. These are implementation constraints, not a claim that any provider endorses this product.

undelete.chat keeps only messages that a platform reports as deleted. Each collector still has to receive the original message and its edits while it is connected, because deletion notices rarely carry content; those copies are held in the encrypted watch buffer and discarded after the owner's watch window unless a deletion arrives. The notes below describe how each platform delivers messages, edits, and deletions to a linked session.

- **Telegram:** [API edit updates](https://core.telegram.org/constructor/updateEditMessage) expose the new message; [delete updates](https://core.telegram.org/constructor/updateDeleteMessages) can contain only message IDs. The collector uses account-scoped IDs for non-channel chats and separate scopes for channels so chat-less deletes can match previous captures. [Telethon's event documentation](https://docs.telethon.dev/en/stable/modules/events.html#telethon.events.messagedeleted.MessageDeleted) notes that deletion updates are not always delivered. The implementation uses the maintained [teleproto library](https://docs.teleproto.dev/migrating-from-gramjs). [Telegram API terms](https://core.telegram.org/api/terms) require care for privacy and prohibit preventing self-destructing content from disappearing; self-destructing media is excluded here, while messages in chats with an auto-delete timer are treated as ordinary messages and kept only if the sender deletes them. Ordinary-message archival still needs product/terms review before broad commercial distribution.
- **Signal:** [Signal's linked-device architecture](https://signal.org/blog/a-synchronized-start-for-linked-devices/) makes a linked device the endpoint that can read messages. There is no Signal-hosted archive API implemented here. The companion uses the unofficial [signal-cli JSON-RPC interface](https://github.com/AsamK/signal-cli/blob/master/man/signal-cli-jsonrpc.5.adoc), including startLink, finishLink, incoming envelopes, edit messages and remoteDelete timestamps. Pairing is explicit and isolated from existing Signal desktop state.
- **WhatsApp:** The implementation uses the unofficial [Baileys project](https://github.com/WhiskeySockets/Baileys), not Meta's Business Platform. Baileys emits an edited-message wrapper for edits and a revoke message stub on `messages.update`. The normalizer distinguishes these from delivery receipts and reactions. This route can break as the protocol changes and has account-policy risks. Business APIs should not be presented as providing universal access to a person's private WhatsApp chats.

## Staying linked without repeated sign-ins (researched September 12, 2026)

- **WhatsApp.** There is no official API for a personal account's chats; the Business Platform serves business numbers and cannot read a personal account. With multi-device, a linked device stays logged in indefinitely; WhatsApp only logs linked devices out when the phone itself has not connected for about two weeks, when the user removes the device, or when the account is restricted. So a hosted Baileys session does not need repeated sign-ins by design. Re-links happen for three reasons, all of which the product now surfaces as a clear error: a stale Baileys release after a protocol change, a ban, or the phone being offline too long. Keeping Baileys current on the monthly pass is the lever we control. Baileys also supports pairing by an 8-character code typed into the phone instead of a QR, which is easier on mobile but does not change persistence.
- **Signal.** No official API. A linked device (signal-cli) stays linked as long as it keeps connecting; Signal removes linked devices only after roughly a month of inactivity, which a hosted, always-on device never reaches. Signal's servers do reject client builds that fall too far behind, so signal-cli must be bumped periodically; the monthly pass covers it. No re-scan is otherwise needed.
- **Telegram.** MTProto sessions persist until terminated from the phone's Devices list, by Telegram's abuse systems, or by the user's inactivity setting. Telegram additionally offers an official, sign-in-free path: a **Telegram Business bot connection**. A user with Telegram Premium connects our bot once from Settings → Telegram Business → Chatbots, chooses which private chats it may see, and the Bot API then delivers `business_message`, `edited_business_message`, and `deleted_business_messages` updates for those chats. Deleted-message updates carry message ids only, which is exactly what the watch buffer needs. Limits: private chats only (no groups or channels), Premium required, one shared bot for all users, and the exact coverage of the user's own outgoing messages must be confirmed with a live Premium account. This is the most promising official integration in the whole product and would remove QR sign-ins and session revocations for Telegram entirely; it has not been built yet.

## Device mode from notifications (Android)

Android's notification listener API exposes the messaging-style notifications each app posts: conversation title, per-message sender, text, and the platform's own message timestamp. WhatsApp, Telegram, and Signal all post this style. WhatsApp replaces a message's notification text with "This message was deleted" when the sender deletes for everyone while the notification is still showing, and updates the text for edits; Signal and Telegram mostly withdraw the notification instead, which is indistinguishable from the user reading the chat and is therefore not treated as a deletion. Coverage is bounded by what produced a notification: muted chats, the chat currently open on screen, and messages read on another device first never appear, and group notifications are truncated to the last few messages. iOS offers no equivalent API to third-party apps. Device mode is therefore a local, account-free complement to the cloud archive rather than a replacement.

For each implemented platform, the useful product promise is recovery of deleted messages **whose content and deletion were both received by a running, authorized collector**. No software can reconstruct an unseen earlier revision from a later deletion notice alone. Attachments are represented by metadata in this version; media downloads and additional content types require separate implementation.
